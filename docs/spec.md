## Claude Code へ：体制と進め方（最初に読むこと）

この仕様書があなたへの発注書。目標は**最速で、最高の UI/UX のプロダクトを仕上げる**こと。ただし「最速」とは手戻りが最少という意味であり、テストや本書の合格条件を飛ばすことではない。飛ばした分は必ず後で倍になって返ってくる。

### 体制：サブエージェントでチームを組む（モデル指定つき）

本体（リード）は **Opus** で起動する（`claude --model opus`）。本体は会話の途中で自分のモデルを変えられないため、**Fable が必要な仕事は本体でやらず、`model: fable` を指定したサブエージェントに委譲する**。これで人手の切替なしに「要所だけ Fable」が自動で成立する。

| エージェント | model | 担当 |
|---|---|---|
| リード（本体） | opus | フェーズ管理、統合、PR 作成、仕様との突合、委譲の采配 |
| architect | **fable** | スキーマ・exclusion 制約・RLS・空き枠エンジン・台帳ロジックの設計と中核実装。**フェーズ0-1・9・17-18 の中心** |
| reviewer | **fable** | 全 PR のレビュー。**read-only（Edit / Write は与えない）** |
| db-foundation | inherit | マイグレーション、シード、CI |
| public-ui | sonnet | 公開ページ一式。第12-1章のデザイン定義に従う |
| admin-ui | sonnet | CMS・電話受付・配車ボード・マイページ。第12-2章 |
| qa | sonnet | テスト作成と実行、第15章の網羅確認、grep 検査 |

運用ルール：

- **フェーズ0の最初の仕事として、`.claude/agents/` に上記6体を `model:` フィールドつきで作成し、コミットする**
- フェーズ0-1・9・17-18 は、まず architect に設計と中核実装を委譲し、その成果物を前提に UI・テストを sonnet 部隊で並行させる
- **すべてのフェーズは、PR 作成前に reviewer（fable）のレビューを通す。指摘の修正までがフェーズの完了条件**
- 利用上限に近づいたら sonnet の比率を上げて凌ぐ。fable を外すのは reviewer を最後にする

並行化の指針：フェーズ間には依存があるため、**同一フェーズ内の縦割り（ロジック / UI / テスト）で並行させる**のが安全。git worktree を使う場合、スキーマ変更（マイグレーション）だけはリードが一元管理し、競合を作らない。

### 自動進行

- **「実装 → QA → reviewer レビュー → 修正 → PR 作成 → 次フェーズ」を、発注者の指示を待たずに連続で進める**
- 止まってよいのは次の3つだけ：
  ① 金銭・個人情報・法令に関わる判断
  ② 環境変数・アカウント・API キーなど、発注者にしか用意できないもの
  ③ CI の失敗を3回試して直せないとき
- それ以外の判断は README の「判断ログ」に残して進む
- フェーズ完了ごとに、PR の URL・プレビュー URL・判断ログの差分を**1つのメッセージにまとめて**報告する。細かい途中経過で発注者を呼ばない

### 権限（発注者決定：bypassPermissions で走らせる）

- 完成確認までは **bypassPermissions で全自動**とする。権限プロンプトで作業を止めない。完成確認後に権限設定を締め直す
- ただし、無確認運用の前提として次を必ず守る：
  1. **DB は開発用 Supabase プロジェクトのみに接続する。** 本番用プロジェクトは完成確認まで作らない・触らない（無確認で破壊的 SQL が走っても失うものが無い状態を保つ）
  2. 作業はリポジトリ内で完結させる。リポジトリ外のファイル・システム設定に触らない
  3. `.env` と API キーは絶対にコミットしない（第1-1章）。キーが履歴に入ったら作業を止めて報告する
  4. `main` へは PR 経由でのみマージする（直接 push 禁止は継続）
- 起動コマンド：`claude --model opus --dangerously-skip-permissions`

### スキルを自由に使う

- 利用可能なスキル（frontend-design など）を**毎フェーズ確認し、該当があれば必ず使う**
- 繰り返すパターンは**プロジェクトスキルとして自作**する。最低限この3つ：
  1. **追記専用台帳の実装パターン**（回数券・ポイント・報酬で3回使う。1回目で固めて使い回す）
  2. **フィールド定義駆動のフォーム生成**（セラピスト・ページ・エリアで使い回す）
  3. **本書のデザイントークン**（第12章の配色・書体・余白をスキル化し、全画面で参照する）
- 最初に `CLAUDE.md` を作る：docs/spec.md への参照、起動・テストコマンド、規約、デザイントークン、「やらないこと」（第16章）の要約

### UI/UX の仕上げ方

- **スクリーンショット駆動で自己レビューする。** 画面を作ったら必ず描画して自分の目で見て、直してから次へ。コードだけ見て完成にしない
- 公開側は**スマホ幅（375px）で先に作る**。管理側は 1280px、マイページはスマホ
- 各画面の完成条件：第12章の配色・書体に一致 / **空状態・ローディング・エラーの3状態が実装済み** / 該当画面はキーボード操作可 / 公開側 LCP 2.5秒以内
- アニメーションは仕様の範囲内のみ。足さない

### 判断に迷ったら

- まず本書の該当章。書いてなければ **README の「判断ログ」に判断と理由を残して進んでよい**。作業を止めない
- ただし**金銭・個人情報・法令に関わる判断だけは、止めて発注者に質問する**

### 進行

1. 本書を `docs/spec.md` としてコミット
2. `CLAUDE.md` を作成
3. フェーズ0から着手。**各フェーズ = PR 1本**、PR 本文に合格条件と確認手順を貼る
4. フェーズ完了ごとにプレビュー URL を報告する

## 0. 前提と、この案件の勝負どころ

**店舗型ではなく派遣（出張）型。** 施術場所は顧客の自宅・ホテル。したがって、

- 「ベッドが空いているか」ではなく **「移動を挟んで次の予約が入るか」** が予約可否を決める
- セラピストの位置は1日を通じて動き続ける。空き枠は**顧客の住所が決まって初めて確定する**
- 同じ時間帯でも、渋谷の顧客には案内できて、八王子の顧客には案内できない

**このシステムの核は「空き枠算出エンジン」（第5章）。** ここが正確でなければ、遅刻とダブルブッキングが日常的に発生して事業が回らない。実装時間の配分もここに厚く割く。

**もうひとつの柱がセラピストの指名。** 顧客はコースではなく人を選んで予約する。だから公開ページの主役はセラピストの個人ページであり、そこに載る情報を運営が自由に増やせる CMS が必要になる。

つくる順番は **公開ページ → CMS → 空き枠エンジン → 予約 → 運用**。裏の会計機能は後回しでよい。

## 1. リポジトリと技術スタック

### 1-1. リポジトリ

```
https://github.com/rocken318/deli01
```

- `main` は常にデプロイ可能な状態を保つ。直接 push しない
- 作業は `feat/フェーズ番号-内容` ブランチを切り、**フェーズ1つ = PR 1本**にする。まとめない
- コミットメッセージは Conventional Commits（`feat:` `fix:` `chore:` `docs:` `test:`）
- PR には「何を実装したか」「どう確認したか」「未対応の点」を書く
- CI（GitHub Actions）：型チェック、lint、テスト。**通らない PR はマージしない**
- **`.env` は絶対にコミットしない。** `.env.example` にキー名だけ置く。API キーが履歴に入ったら、rotate するまで作業を止める
- `main` へのマージで Vercel の本番デプロイが走る。PR ごとにプレビューを出す

### 1-2. 技術スタック（指定）

- **Next.js 15 App Router + TypeScript strict**
- **PostgreSQL**（Supabase）+ **PostGIS**（住所の座標と距離計算に使う）
- **Drizzle ORM** — マイグレーションは SQL としてリポジトリに残す
- **Supabase Auth**（管理側のみ。顧客ログインは任意、第8章参照）
- **Tailwind CSS**
- **date-fns / date-fns-tz** — 全処理 `Asia/Tokyo`
- **Zod** — 全 Server Action の入力を検証。型だけで通さない
- 地図：**Google Maps Distance Matrix API**（ただし第5章の方針に従い、常時は叩かない）
- テスト：Vitest（統合テストは実 Postgres）、Playwright（E2E）
- デプロイ：Vercel

**禁止**
- 金額に小数を使わない。すべて整数（円）
- `any` を書かない
- クライアントから直接 DB を触らない
- 日時を文字列で計算しない。DB は `timestamptz`

## 2. 公開ページ（最初に作る）

**本章に出てくる文言・見出し・画像は、すべて CMS から変更できるものとして作ること**（第3-6章）。以下は初期状態の説明であって、固定仕様ではない。

### 2-1. 画面構成

```
/                     トップ。いま出勤中のセラピスト、最短で案内できる時間
/therapists           セラピスト一覧（絞り込み：エリア / 日時 / 得意な施術 / 指名可否）
/therapists/[slug]    セラピスト個人ページ ★ 主役
/schedule             出勤表。日別に誰が派遣可能か ★
/courses              コース・オプションと料金
/areas                対応エリアと交通費
/booking              予約フロー
/guide, /faq          利用の流れ、よくある質問
```

### 2-2. セラピスト個人ページ

**このページに載る項目は、すべて CMS 側で足したり消したりできること。** 以下は初期セットであって固定仕様ではない。

- 写真（複数枚）
- 名前 / ふりがな / ニックネーム
- キャッチコピー（1行）
- 自己紹介（リッチテキスト）
- **得意な施術**（複数選択タグ。例：オイル / 指圧 / リンパ / ストレッチ / 足つぼ）
- 保有資格
- 経験年数
- 対応可能エリア
- 対応コース
- 指名料
- **出勤予定**（下記）
- **いま予約できる最短の時間**（下記）

### 2-3. 出勤・空き枠の表示

**ここが公開ページの心臓部。**

- 直近2週間の出勤予定をカレンダーで出す。出勤時間は CMS で設定したものがそのまま反映される
- 各日について、**空いている時間帯を帯で表示**する
- ただし出張型なので、**表示している空き枠がそのまま予約できるとは限らない。** 顧客の住所によって移動時間が変わるため
- したがって公開ページの空き枠は **「〇〇区であれば案内可能」という前提つき**で表示し、その旨を明記する。エリアを選ぶと表示が絞り込まれる
- 顧客が住所を入力した時点で、**その住所を前提に再計算した確定枠**を出す
- **嘘の枠を出さない。** 予約できない時間を「空いています」と見せるのは、この事業でいちばんやってはいけないこと

### 2-4. 一覧ページの絞り込み

- 日時（今すぐ / 今夜 / 日付指定）
- エリア（区・市、または最寄り駅）
- 得意な施術（CMS のタグから自動生成）
- コース
- 「今から2時間以内に来られる人」

### 2-7. キャッシュ方針

情報の性質が違うので、分けて扱う。

| 対象 | 方針 |
|---|---|
| プロフィール本文・写真 | ISR。CMS で公開したときに on-demand revalidate |
| 出勤予定 | 60秒キャッシュ |
| 空き枠・最短案内時間 | **キャッシュしない。** 毎回計算する |

プロフィールと一緒に空き枠を静的化してはいけない。古い枠を見せることになる。

## 3. CMS（管理画面）

### 3-1. 自由に項目を足せる仕組み

**方式：フィールド定義テーブル + JSONB。** EAV（縦持ち）にはしない。検索性と実装の複雑さが割に合わない。

```sql
-- 項目の定義
field_definitions (
  id            uuid pk,
  entity        text not null,        -- 'therapist' | 'course' | 'area'
  key           text not null,        -- 'good_at', 'years_of_experience'
  label         text not null,        -- 画面に出す名前
  type          field_type not null,
  options       jsonb,                -- select の選択肢、数値の範囲など
  group_label   text,                 -- 「プロフィール」「スキル」などの見出し
  sort_order    integer not null,
  is_public     boolean not null,     -- 公開ページに出すか
  is_required   boolean not null,
  is_filterable boolean not null,     -- 一覧の絞り込みに使うか
  help_text     text,
  unique (entity, key)
)

-- 値は対象テーブルの jsonb カラムに入れる
therapist_profiles (
  therapist_id  uuid pk,
  slug          text unique not null,
  draft         jsonb not null,       -- 編集中
  published     jsonb,                -- 公開中。null なら未公開
  published_at  timestamptz,
  ...
)
```

**`field_type` に用意するもの**
`text` / `textarea` / `rich_text` / `number` / `boolean` / `select` / `multi_select` / `tag` / `image` / `image_gallery` / `date` / `url` / `money`

**実装の要点**
- 管理画面のフォームは `field_definitions` から**動的に生成**する。項目を足したらフォームに自動で現れること。コード変更を伴ってはいけない
- 入力検証は定義から **Zod スキーマを実行時に組み立てて**行う
- 公開ページの表示も定義駆動。`is_public` と `sort_order` に従って並べる
- `is_filterable` な項目は一覧の絞り込み UI に自動で現れる。`published` に GIN インデックスを張る
- **項目の削除は論理削除。** 既存の値を巻き添えで消さない。「非表示にする」と「完全に削除する」を分け、後者は二段階確認
- `key` の変更は禁止。ラベルだけ変えられる

### 3-2. 下書きと公開

- `draft` を編集 → プレビュー → 公開で `published` へコピー
- プレビューは実際の公開ページと同じコンポーネントで、署名付き URL から見る
- 公開時に該当ページを revalidate
- 変更履歴を残し、直前の版に戻せること

### 3-3. 出勤設定

- セラピストごとに月カレンダーで出勤時間を入れる
- **繰り返しパターン**（毎週火木、隔週など）を登録して一括生成
- 1日の中で **待機開始場所** と **待機終了場所** を指定する（自宅／最寄り駅／事務所）。移動時間の計算に使う
- **その日に対応できるエリア**を指定する（全域とは限らない）
- 1日の最大施術本数、連続施術の上限
- 保存した瞬間に公開ページへ反映される（キャッシュ60秒）
- **当日の急な欠勤**：ワンタップで「本日休み」。既存の予約がある場合は一覧で見せて、振替を促す

### 3-4. オプション

延長・アロマ追加・指圧強めなど。**コースとは別の実体**として持つ。カスタムフィールドの仕組みは使わない。価格・時間・バックを持つので専用テーブルにする。

```sql
options (
  id, name, description,
  price          integer not null,
  duration_min   integer not null,   -- 施術時間への加算。0 も可
  back_type      -- 'fixed' | 'rate'
  back_value     integer,            -- セラピストへのバック
  is_public      boolean,
  sort_order     integer,
  is_active      boolean
)
option_availability (option_id, therapist_id)  -- 空なら全員対応
reservation_options (reservation_id, option_id,
  price_snapshot, duration_snapshot, back_snapshot)
```

- CMS から自由に追加・並べ替え・公開停止できる
- **`duration_min` が空き枠計算に効く。** +30分のオプションを付けたら、その分だけ次の予約との間隔が要る。第5章のアルゴリズムの `L` はコース時間ではなく **コース + オプション合計**
- **当日その場で追加される延長が、この業態の最大の運用リスク。** 施術中に延長が入ると次の予約に間に合わない。セラピスト用画面に「延長を追加」を置き、押した瞬間に後続予約への影響を判定して可否を返すこと。不可なら追加させない（管理者承認で上書き可、理由必須）
- 価格・時間・バックはすべて予約側にスナップショットする。後からオプションの値段を変えても過去の予約は変わらない

### 3-5. 出退勤（実績）

**予定と実績を分ける。** `shifts` は予定、`attendances` は実績。混ぜてはいけない。

```sql
attendances (
  id, therapist_id, work_date,
  clock_in_at, clock_out_at,
  clock_in_location, clock_out_location,  -- 任意。同意した人のみ
  status, note
)
```

- セラピスト用スマホ画面からワンタップ打刻
- 予定と実績の差分を管理画面に出す（遅刻・早退・未出勤）
- 打刻が無いまま最初の予約の出発時刻が近づいたらアラート
- 目的は労働時間の管理ではなく、**「今日は誰が実際に動けるのか」の把握、安全確認、予定精度の改善**

**注意：業務委託者に対する細かい勤怠管理は、契約上の論点になりうる。** 時間で縛る運用は労働者性の判断に影響する可能性がある。打刻は「稼働の可視化」として設計し、遅刻に対する制裁のような機能は作らない。位置情報の取得は任意・同意ベースとし、目的外に使わない。この点は社労士に確認すること。

### 3-6. 公開ページのコンテンツ管理 ★

**公開ページに出る文言と画像は、原則すべて CMS から変えられること。** コードに直書きされた日本語が残っていたら不合格。レビュー時に grep で確認する。

3層に分けて扱う。混ぜない。

| 層 | 対象 | 方式 |
|---|---|---|
| グローバル設定 | 屋号、ロゴ、受付電話番号、受付時間、SNS、フッター、ナビゲーション | キー・バリュー |
| ページ単位のフィールド | 各ページの見出し、リード文、ヒーロー画像、CTA文言、SEO情報 | `field_definitions` を `entity='page'` で再利用 |
| ブロック | トップや案内ページの自由な区画 | ブロック配列（jsonb） |

**フィールド定義の仕組みは第3-1章のものをそのまま使い回す。** 二重に作らない。

**ブロックは種類を限定する（ホワイトリスト）**

`hero` / `text` / `image` / `text_image` / `therapist_picks` / `course_list` / `steps` / `faq` / `notice` / `cta`

- 並べ替え、複製、非表示ができる
- **これ以上は増やさない。** 何でも置けるページビルダーにすると、必ずデザインが崩れて誰も直せなくなる。増やしたくなったらコードで型を追加する
- 各ブロックは決められたレイアウトの中でしか組めない。**幅・色・フォントは選ばせない**

**CMS で触らせないもの**（固定する）

- 予約ボタンの位置と動作
- 料金の計算と表示のロジック
- 空き枠の表示
- 法定表記ページの必須項目

文言を変えられれば十分で、構造まで開放すると事故る。

**その他**

- お知らせ・バナーは**掲載期間を指定して自動で出し入れ**する（年末年始、キャンペーン）。手で消し忘れるのを防ぐ
- ページごとに SEO の title / description / OGP 画像を持つ。未設定時のフォールバックを用意する
- **公開予約**（指定日時に公開）ができること
- 下書き・プレビュー・履歴・巻き戻しは第3-2章の仕組みを共用する
- **禁止語チェック（第13-2章）はサイト文言にも同じくかける。** セラピストのプロフィールだけではない
- 公開すると該当ページを revalidate する
- 特商法表記・プライバシーポリシー・キャンセルポリシーは雛形を入れておき、編集可能にする
- **多言語の下準備**：`pages`・用語辞書・お知らせに `locale` カラムを持たせる（既定 `ja`）。今回の実装は日本語のみだが、後から英語版を足すときにスキーマの作り直しにならないようにする

### 3-7. メディア（画像）★

- Supabase Storage にメディアライブラリを作る。アップロード、タグ付け、検索、差し替え
- アップロード時に**自動で WebP 変換と複数サイズ生成**。公開側は `next/image` で配信
- **alt テキストを必須入力にする。** 未入力では公開できない
- 差し替えても ID と URL を保つ。掲載箇所を全部直して回らずに済む
- 容量上限と、未使用メディアの一覧

**ダミー画像（開発・デモ用）**

- シードでヒーロー・コース案内・セラピストのダミー画像を**メディアライブラリ経由で登録**する。`public/` への直置きは禁止。**ダミーの時点で「CMS から差し替えられること」を実証する**のが目的
- **人物のダミーに実在の人物写真を使わない。** フリー素材でも不可。肖像権の問題と、本番への混入事故を避ける。ビルド時に生成する抽象シルエット＋イニシャルのプレースホルダ SVG を WebP 化して使う
- ヒーローとコース案内は、生成した抽象グラデーション＋小物モチーフの SVG でよい（トーンは第12-1章の配色に合わせる）
- すべてのダミー画像に alt を入れる（alt 必須の実証を兼ねる）
- README に**「本番公開前にダミー画像をすべて差し替える」チェックリスト**を載せ、ダミーが残ったまま公開できないよう、ダミー画像にはタグ `placeholder` を付けて一覧で追えるようにする

**セラピスト写真の扱い（実務でここが問題になる）**

- **掲載同意フラグと同意日を持つ。** 同意の無い写真は公開できない
- 退職・契約終了時に、**そのセラピストの画像と公開プロフィールを一括で非公開にする**操作を1つ用意する。個別に消して回らせない
- 顔出し可否（顔出し / 目線入り / 顔なし）をセラピストごとに設定し、公開側の表示に反映する

### reservations の要点

```sql
id                  uuid pk
therapist_id        uuid not null

address_id          uuid not null

free_at             timestamptz not null   -- 次へ動ける時刻 ★
travel_in_min       integer not null       -- 計算時に使った移動時間（控え）
travel_out_min      integer not null
buffer_min          integer not null

nomination_fee      integer not null
transport_fee       integer not null
total_amount        integer not null
version             integer not null       -- 楽観ロック
```

**`depart_at` と `free_at` を必ず持つこと。** 施術時間だけを持つと、移動中が空き時間に見えてしまう。

**セラピストの時間重複は DB 制約で止める。** アプリのチェックだけでは同時リクエストで抜ける。占有区間は `start_at`〜`end_at` ではなく **`depart_at`〜`free_at`** で判定する。

```sql
create extension if not exists btree_gist;

alter table reservations add constraint no_therapist_overlap
  exclude using gist (
    therapist_id with =,
    tstzrange(depart_at, free_at, '[)') with &&
  ) where (status in ('held','confirmed','enroute','in_service','done'));
```

制約違反は**「他のお客様の予約が先に確定しました」という日本語**に変換して返す。生の Postgres エラーを画面に出さない。

## 5. 空き枠算出エンジン ★ 最重要

`src/domain/availability/` に独立したモジュールとして実装する。**DB にも Next.js にも依存しない純粋関数**にすること。テストしやすさが品質を決める。

### 5-1. 移動手段は徒歩と車の2つ

徒歩と車では所要時間の決まり方がまったく違う。**同じ仕組みで扱ってはいけない。**

| | 徒歩 | 車 |
|---|---|---|
| 時間の決まり方 | 距離にほぼ比例。ばらつきが小さい | 経路と時間帯に依存。ばらつきが大きい |
| 時間帯の影響 | ほぼ無し | 大きい。**深夜は速くなる** |
| 到着後の追加時間 | ほぼ無し | **駐車場探しが読めない** |
| 必要な粒度 | 町丁目・駅単位 | 区・市単位で足りる |

**徒歩：マトリクスを作らない。PostGIS で毎回計算する。**

徒歩圏を区単位のマトリクスで扱うと精度が出ない。同じ区の中でも端から端では30分違う。かといって町丁目単位でマトリクスを組むと数万件になり保守できない。距離から計算するほうが正確で、しかも保守が要らない。

```
徒歩時間(分) = 直線距離(m) × 迂回係数 ÷ 分速

  迂回係数  1.30   （既定。CMS で調整可）
  分速      80 m/分（既定。道具を持って歩くので通常より遅めに置く）
```

- 座標は住所のジオコーディング時に取得し、`addresses` に PostGIS の `geography` で保存する
- **徒歩上限（既定 1.6km / 約25分）を超えたら車に切り替える。** 閾値は CMS で調整可能
- 川・線路・幹線道路で分断されている区間は迂回係数が効かない。**該当区間だけ CMS で個別に上書きできる**ようにする（例：この町丁目間は橋を渡るので +12分）。上書きは区間単位の例外テーブルで持つ

**車：エリア間マトリクス + 時間帯係数。**

```sql
area_travel_times (
  from_area_id uuid, to_area_id uuid, minutes integer not null,
  primary key (from_area_id, to_area_id)
)

travel_time_modifiers (
  time_from time, time_to time,
  multiplier numeric, additional integer
)
```

- 初期値は Distance Matrix API で一括生成し、**CMS で人手で上書きできる**ようにする。現場の実感のほうが正確なことが多い
- **深夜の係数は 1 を下回る。** 道が空くので昼より速い。0.75 あたりから始めて実績で調整する。朝夕の通勤帯は逆に 1.3〜1.5
- 未登録のエリア間は直線距離 × 係数で暫定値を出し、管理画面に「要設定」として一覧表示する

**セラピストごとの設定**
- 車を使えるか（免許・車両の有無）。使えない人は徒歩圏内の予約しか受け付けない
- 徒歩上限の個人差（速い人／短くしたい人）

**エリア設計への含意**：徒歩が基本なら、セラピストは広く薄くではなく**狭い範囲に濃く**配置したほうが稼働率が上がる。管理画面に「エリア別の対応可能人数」を出して、配置の偏りが見えるようにすること。

### 5-2. バッファ

移動時間の他に、必ずバッファを入れる。

| 種類 | 徒歩 | 車 | 内容 |
|---|---|---|---|
| 到着前 | 10分 | 10分 | 建物探し、エレベーター、インターホン |
| **駐車** | — | **15分** | 駐車場探し・駐車・戻り |
| 施術前 | 5分 | 5分 | 挨拶、カウンセリング、準備 |
| 施術後 | 10分 | 10分 | 片付け、会計、見送り |

すべて CMS で変更可能にし、**エリア別に上書きできる**こと（都心の駐車バッファは20分、郊外は5分）。

**駐車バッファをケチると、その日の予定が全部後ろにずれる。** 移動時間そのものより読めないのはここ。最初は多めに置き、実績を見て削る。

### 5-3. 算出アルゴリズム

```
入力: therapistId, date, 施術時間 L, 目的地エリア A, 現在時刻 now
      ※ L = コース時間 + 選択されたオプションの duration_min 合計
出力: 予約可能な開始時刻のリスト

1. shift を取得。無ければ空を返す
   → 待機開始場所 B_start, 待機終了場所 B_end, 対応エリア, 上限本数

2. A が対応エリアに含まれるか確認。含まれなければ空を返す

3. 上限本数に達していれば空を返す

4. 既存予約を depart_at 順に並べる → R1..Rn

5. 隙間を列挙する
   gap0  : シフト開始（B_start にいる） → R1.depart_at
   gap_i : Ri.free_at（Ri のエリアにいる） → R(i+1).depart_at
   gap_n : Rn.free_at → シフト終了（B_end へ戻る）

6. 各 gap（直前地点 P、開始可能時刻 t_p、直後地点 N、締切時刻 t_n）について、
   開始時刻 s が満たすべき条件:

     s ≥ t_p + travel(P→A) + buffer_arrive
     s ≥ now + 受付リードタイム（既定90分）
     s + buffer_before + L + buffer_after + travel(A→N) ≤ t_n

   ※ gap_n の N は B_end。「帰れること」まで条件に入れる

7. s を15分刻みに切り上げて列挙

8. すでに held / confirmed の枠と重複するものを除外
```

**このアルゴリズムに対するテストを最優先で書く。** 以下は必ず含めること。

- 空きシフトで、シフト全体が枠になる
- 予約が1本ある日、その前後に移動時間ぶんの余白が空く
- 隣接エリアなら入るが、遠方エリアだと入らない隙間
- 隙間ちょうどに収まるケース（1分の余裕もない）と、1分足りないケース
- 徒歩上限（1.6km）の前後で、徒歩と車が正しく切り替わる
- 深夜の車係数で移動が短くなり、昼は入らない枠が入る
- 駐車バッファが車のときだけ加算される
- シフト終端で「帰れない」枠が除外される
- 上限本数に達した日
- 対応エリア外
- 日跨ぎの予約（23:30開始120分コース）
- 現在時刻が進むと、リードタイム内の枠が消える

### 5-4. 「最短で案内できる時間」

トップページと一覧に出す目玉表示。上記アルゴリズムを `now` 起点で回して最初の1件を取る。
エリアが未指定のときは**代表エリアを仮定して概算**し、「〇〇区の場合」と条件を明記する。

### 5-5. 仮押さえ（これが無いと同時予約で必ず事故る）

公開サイトから予約する場合、顧客が住所や氏名を入力している数分の間に、別の顧客が同じ枠を取る。

```sql
slot_holds (
  id, therapist_id, start_at, end_at, depart_at, free_at,
  session_id, expires_at, created_at
)
```

- 枠を選んだ瞬間に **10分間のホールド**を取る。reservations に `status='held'` で入れて exclusion 制約で守るのが確実
- 残り時間を画面に出す
- 期限切れは cron で解放。あわせて参照時にも期限切れを除外する
- 確定したら `confirmed` に変える

## 6. 予約フロー（公開側）

```
1. セラピストを選ぶ（または「誰でもいい」を選ぶ）
2. 派遣先を選ぶ（住居 / ホテル）→ エリアが決まる → 空き枠を表示
3. コースを選ぶ → 枠を再計算
4. 枠を選ぶ → ホールド開始（10分）
5. 住所を詳細まで入力 → その住所で再計算し、枠が維持できるか確認
   → 維持できなければ、近い代替枠を提示する
6. 氏名・電話番号を入力
7. オプションを選ぶ（時間が伸びる場合は枠を再確認）
8. ポイントを使うか選ぶ（保有していれば）
9. 料金の確認（コース + オプション + 指名料 + 交通費 + 深夜加算 − ポイント）
10. 確定
11. 会員登録の案内（任意。登録しなくても予約は完了する）
```

- **料金は最後まで隠さない。** 各段階で現時点の合計を常時表示する
- 「誰でもいい」を選んだ場合、条件に合うセラピストを提示して選ばせる。運営が勝手に割り当てない
- 確定後の変更・キャンセルは、URL と電話番号でアクセスできるページから行う
- キャンセルポリシー（何時間前から何%）を予約前に明示し、同意を取る

**直前割**

- 当日、指定時刻を過ぎても埋まらない枠に自動で割引を付ける。割引率・対象時間帯・1日の適用上限・対象コースは CMS で設定
- 割引は `discount` のマイナス行として計上する（第10章）。**バック計算の基礎を割引前・割引後のどちらにするかは第11-3章の設定に従う**（既定は割引前。セラピストの手取りを事業側の販促で減らさない）
- 公開側では割引枠にラベルを付けて目立たせる

**キャンセル待ち**

- 満枠のとき、希望条件（日時の範囲・エリア・セラピスト）を登録できる
- キャンセルや変更で条件に合う枠が生まれたら通知する（メール。将来 LINE）
- **通知は「空きました」の案内に留め、先着の仮押さえ権は与えない。** 枠の取り合いは通常の仮押さえ（第5-5章）で処理する

**予約の電話確認（Web 予約は必須）★**

- Web からの予約は、確定後も**「電話確認待ち」**の状態を持つ。受付が電話で本人・住所・時間を確認し、**チェックを付けた予約だけが「確認済み」**になる
- `phone_confirmed_at` / `phone_confirmed_by` を予約に持ち、配車ボードと予約一覧に**チェックマーク**を表示する
- **確認が済むまで、セラピストへ確定情報（住所入り）を送れない。** 打診（個人情報なし）は確認前でも可
- 出発予定の2時間前（CMS で変更可）までに未確認ならアラートを出し、架電リストに載せる
- 架電の記録（`call_logs`：時刻・結果）を残す。既定で**3回不通なら運営判断でキャンセルにできる**。その条件をキャンセルポリシーの雛形に入れ、予約時に同意を取る
- 電話注文は受付が本人と話しているので、保存時に自動で確認済みになる

**リマインド通知**

- 確定時に加え、**前日と当日2時間前**に自動でリマインドを送る（メール。LINE 連携後は LINE）。文面は CMS のテンプレートで編集できる

**計測**

- 「訪問 → セラピスト閲覧 → 枠選択 → 仮押さえ → 確定」をイベント計測し、離脱箇所を集計画面で見られるようにする

### 7-1. 配車ボード

当日の全セラピストを1画面で見る。

- 縦軸が時間、横軸がセラピスト
- 1本の予約を **「移動 → 施術 → 移動」の3ブロック**で描く。移動時間が見えることが重要
- ブロックに顧客名・エリア・コース時間
- ステータスをワンタップで進める：確定 → 移動中 → 施術中 → 完了
- **遅延の検知**：移動中のまま予定開始時刻を過ぎたら赤く光らせ、後続の予約に影響が出る場合は連鎖して表示する
- 電話番号はタップで発信

### 7-2. 手動予約

電話で入る予約を受付が入力する。公開側と同じ空き枠エンジンを使う。
ただし**運営権限では警告つきで枠外の予約も入れられる**ようにする（無理を承知で入れる判断は人間がする）。理由の入力を必須にし、監査ログに残す。

---

### 7-3. セラピストの安全

個人が単独で顧客の私宅を訪問する業態なので、これは福利厚生ではなく**事業継続の要件**。仕組みとして持たせる。

- **到着・退出のワンタップ記録。** 退出予定時刻を過ぎても退出記録が無ければ、管理画面にアラートを出す
- **緊急連絡ボタン。** セラピスト画面に常時表示。押すと管理者へ予約情報が飛ぶ
- **顧客のフラグ管理。** 迷惑行為・要注意の記録を残し、次回予約時に警告する。ブロックした顧客は公開側からも予約できない
- **初回顧客の識別。** 配車ボードで初回訪問が一目で分かること
- 顧客の電話番号がセラピストの個人端末に残らないようにする（アプリ内から発信する、または転送番号を使う）

運用ルールは事業者が決めるが、**記録が取れる仕組みが無ければルールを守らせられない。**

### 7-4. セラピスト用マイページ（スマホ専用）★

各所に散らばっている本人向け機能を、1つの画面に束ねる。**自分に関することは全部ここで済む**こと。

- **今日の予定**：移動 → 施術 → 移動のタイムライン。次の出発時刻を最上部に大きく出す
- 明日以降の予定と、自分の出勤カレンダー
- 打診への返答（受ける / 受けない）
- 出退勤の打刻（第3-5章）
- 施術完了の操作と、引き継ぎメモの入力（第9章）
- **稼ぎ**：本日の確定額、今月の見込み、内訳、過去の支払明細（第11-5章）
- 緊急連絡ボタン（第7-3章）
- 顧客住所は予約の3時間前から表示（第13-3章）

ログインは Supabase Auth。**LINE 連携（ロードマップ24）が入った後は、LINE の通知から期限付きリンクでこの画面に飛ぶ**動線になる。

## 8. 電話受付とセラピストへの送信 ★

電話注文がこの事業の主要な入口。**受付が電話をつなぎながら片手で入力できること**が要件。ページ遷移を挟まず1画面で完結させる。

### 8-1. オーダーエントリー画面

上から下へ一方通行。**Tab キーだけで最後まで入力できること。**

```
電話番号         → 入力した瞬間に既存顧客を検索。ヒットしたら以下を自動で埋める
名前             → 仮名可。「お呼びしてよい名前」だと画面に明記する
派遣先           → 住居 / ホテル を切り替え
  住居のとき     住所・建物名・部屋番号
  ホテルのとき   ホテル名（マスタから予測入力）・部屋番号 ★
セラピスト       → 指名、または対応可能な人から選ぶ
コース           → 選ぶと施術時間が確定
オプション       → 複数選択。時間が伸びるものは即座に反映
希望時刻         → 上記を踏まえた空き枠だけを出す
お好み・自由記入 → 強さ、苦手な部位、要望、注意事項
─────────────────────────
合計金額  コース + オプション + 指名料 + 交通費 + 深夜加算 − ポイント利用
```

- **電話番号を入れた時点でリピーターか分かること。** 過去の住所・好み・担当者・NG が出れば聞き直しが消える
- 合計金額は入力のたびに再計算し、**画面上部に固定表示**する。電話口で即答できることが目的
- 保存で予約が確定し、売上台帳（第10章）とポイント（第9章）に自動で反映される
- **空き枠は公開側とまったく同じエンジンを使う。** 受付だけ別ロジックにしない
- 権限つきで枠外予約も可（理由必須、監査ログ）
- **不成立ログ ★**：成約しなかった電話も「不成立」ボタンで必ず記録する。理由（時間が合わない / エリア外 / 指名不可 / 料金 / その他）をワンタップ選択。**どこで注文を落としているかを数字にする**

### 8-2. ホテルマスタ ★

ホテルは住居と扱いが違う。**マスタを持つと、入力速度と移動時間の精度が同時に上がる。**

```sql
hotels (
  id, name, name_kana, address, location geography, area_id,
  entry_note     text,     -- フロント経由が必要 / 直接部屋へ可
  parking_note   text,     -- 駐車場の有無・料金・距離
  extra_minutes  integer,  -- 到着から部屋までの追加時間
  is_blocked     boolean,  -- 入館お断りの施設
  note           text
)
```

- 1〜2文字から予測入力で絞れること
- **`extra_minutes` を移動バッファに加算する。** 大型ホテルはエントランスから部屋まで10分かかる
- `is_blocked` のホテルは予約を作らせない。公開側でも選べない
- 未登録のホテル名が入力されたら**その場で仮登録**し、後から情報を補完できるようにする。**電話を止めない**

### 8-3. セラピストへの送信テキスト ★

保存後、**ワンタップでコピーできるテキストを生成**する。LINE 等に貼って送る。

- テンプレートは CMS で編集可能。差し込み変数を使う
  `{{日時}} {{出発目安}} {{セラピスト}} {{コース}} {{オプション}} {{場所}} {{部屋番号}} {{顧客名}} {{電話番号}} {{お好み}} {{合計金額}} {{バック額}} {{移動手段}}`
- **テンプレートは2種類用意する**
  - **打診用**：エリア・時間・コース・バック額のみ。**住所と電話番号を含まない**
  - **確定用**：住所・部屋番号・顧客名・お好みを含む
- 打診 → 受諾 → 確定用を送る、の順で運用する

**ここに設計上の緊張がある。** 第7-3章では「顧客の電話番号をセラピストの個人端末に残さない」と書いた。LINE に貼れば端末に残る。両立しないので、こう整理する。

- 打診段階では個人情報を出さない（上の2段階テンプレート）
- 確定用を送るのは**出発直前**にする
- **送信ログを残す。** 誰の情報を、いつ、誰に渡したか。監査ログの対象
- 将来 LINE Messaging API で自動送信し、施術完了後に自動削除する運用へ移せるよう、**テキスト生成は独立した関数（`buildDispatchMessage`）に切り出す。** 今回はコピペまで

- コピーボタンを押したら「送信済み」として記録し、配車ボードに反映する

## 9. 顧客・指名・ポイント

### 顧客
- 電話番号で名寄せ。ログイン必須にはしない（離脱率が上がる）
- マイページは「予約番号 + 電話番号」でアクセス。任意でアカウント登録できる
- 住所は複数登録可（自宅・ホテル）。**次回以降の入力を省けることが体験を大きく変える**
- 指名NGのセラピストを設定でき、その組み合わせは公開側でも予約できない

**施術後の引き継ぎメモ**

- 施術完了時にセラピストが一言残す（圧の好み、会話の話題、注意点）。`handover_notes` に顧客と紐づけて保存
- 同じ顧客の次回予約時に、**担当セラピストにだけ**自動表示する。顧客住所と同じ扱いで、無関係のセラピストには見せない
- 個人情報の開示請求で本人の目に触れる可能性があるものとして扱う。**人格・容姿への言及を禁止する注意書き**を入力欄に常時表示する

### 指名
- 指名料はセラピストごと・コースごとに設定
- 顧客の指名回数、直近の担当者を管理画面から見られる
- リピート率と指名率をセラピスト別に集計

### ポイント ★

**回数券と同じく、残高をカラムで持たない。追記専用台帳にする。**

```sql
point_entries (
  id, customer_id,
  type,          -- 'earn'|'use'|'expire'|'adjust'|'reverse'
  points  integer not null,   -- earn:+ / use:−
  reservation_id, reason,
  expires_at,                 -- 付与単位で期限を持つ
  occurred_at, created_by
)
```

- 残高 = `sum(points)`。重ければ `customers.cached_points` をトリガで更新。**正は台帳**
- **期限は付与単位で持ち、古いものから消費する（先入先出）**
- 付与ルールは CMS で設定：金額あたりの率、コース別、指名ボーナス、初回、誕生月、紹介
- 会員ランク（累計利用額または回数）で付与率を変える
- 利用は 1P=1円の値引き、または一定Pでコース割引。**1回の利用上限・下限を設定できること**
- 失効は日次バッチ。**失効30日前の対象一覧**を出せること（連絡のため）
- **電話注文でも貯まり、使えること。** 電話番号で識別する。会員登録は任意

**会計と報酬への連動（ここを間違えると数字が合わない）**

1. ポイント付与は売上を減らさない。**引当（負債）として別に積む**
2. ポイント利用は `discount` として**マイナスの `revenue_line`** を立てる
3. **ポイント利用分をセラピストのバック計算基礎に含めるかを設定できること。** 既定は「含める」。施術内容は同じなので。回数券とまったく同じ論点
4. 失効ポイントは引当の戻入として計上する

## 10. 会計・売上

- 支払方法：現金 / カード / 電子マネー / 回数券。**1予約で併用可**
- コース料金・オプション・指名料・交通費・深夜加算を、それぞれ独立した行として計上する。合算しない
- 回数券は**追記専用台帳**（`ticket_entries`）で管理し、残回数はカラムで持たない。取り消しは逆仕訳の追加
- 集計は `revenue_lines` だけを読む。予約テーブルを直接集計しない

**集計（期間 × エリア × セラピスト）**

- 総売上、件数、客単価、支払方法内訳、前受金残高（回数券・ポイント引当）
- セラピスト別：件数、売上、指名率、リピート率
- 新規 / リピート比率、離脱顧客（90日以上未利用）
- 時間帯別・曜日別の成約ヒートマップ
- **需要ヒートマップ**：不成立ログ × 曜日 × エリアで「取り逃した需要」を可視化し、供給ボード（第2-5章）と重ねる。出勤調整と採用の判断材料
- CSV 出力（UTF-8 BOM 付き）
- **経費入力**：オイル・備品・駐車場代・広告費をカテゴリ付きで入力する（`expenses`）。突合（第11-6章）の「経費」はここから取る
- **週次レポート**：毎週月曜の朝、先週の売上・稼働率・不成立件数・失効間近の回数券 / ポイントをオーナーへ自動メールする

## 11. 報酬（業務委託バック）★

セラピストは原則として業務委託。**1件ごとのバックが報酬の中心**になる。ここが不透明だと人が辞めるので、金額そのものより「なぜその額になったか」を説明できることを最優先に設計する。

### 11-1. レート

```sql
payout_rates (
  id,
  therapist_id    uuid,      -- 個別レート
  rank_id         uuid,      -- ランク別レート
  target_type,               -- 'course'|'option'|'nomination'
                             -- |'transport'|'late_night'|'cancel_fee'
  target_id       uuid,      -- コースID・オプションIDなど
  calc_type,                 -- 'fixed'（円） | 'rate'（率）
  value           numeric not null,
  effective_from  date not null,
  effective_to    date
)
```

- 優先順位は **個別レート > ランク別 > 既定**
- **レートは適用開始日を持ち、過去に確定した報酬を絶対に書き換えない。** 遡って変わると信用を失う
- 指名料のバック率は通常施術と別に設定できること（指名料を全額バックにする事業者は多い）
- 深夜加算、オプション、交通費もそれぞれ別レート
- 交通費は「実費支給」「本人負担」をエリア・コース単位で選べる

### 11-2. 台帳

```sql
payout_lines (          -- 追記専用。修正は逆仕訳
  id, therapist_id, business_date, reservation_id,
  category,             -- 'course'|'option'|'nomination'|'transport'
                        -- |'late_night'|'cancel_fee'|'adjustment'
  amount     integer not null,
  calc_note  jsonb not null,   -- 計算根拠のスナップショット ★
  created_at, created_by
)
```

**`calc_note` に、使ったレート・元金額・計算式をそのまま残すこと。** 「90分コース 12,000円 × 45% = 5,400円、レートID xxx、適用日 2026-04-01」まで書く。ここを残していないと、報酬について問われたときに答えられず、必ず揉める。

### 11-3. 間違えやすいルール

1. **回数券を消化した施術でもバックは発生する。** 顧客はその場で現金を払っていないが、施術は行われている。売上（前受金の振替）とバックを混同しない。**ここを取り違えると、回数券の日だけセラピストの報酬が消える**
2. キャンセル料が発生した場合のバック配分を設定できること（既定は一部）
3. 無断キャンセル（noshow）で移動だけ発生した場合の扱いを決めておく。既定は交通費のみ支給
4. 値引きした場合、バックの計算基礎を「値引き前」「値引き後」のどちらにするか設定できること。ここは事業判断
5. 締めたあとの `payouts` はロックする。修正は逆仕訳のみ

### 11-4. 締めと支払

```sql
payouts (
  id, therapist_id, period_start, period_end,
  gross, deductions, net, status, closed_at, paid_at
)
payout_deductions (payout_id, kind, amount, note)  -- 立替・備品・貸付
```

- 締め日・支払日は CMS で設定
- 支払明細を PDF / CSV で出力。**全銀フォーマットの CSV 出力まではやる。振込の実行はしない**
- **インボイス制度**：セラピストごとに適格請求書発行事業者の登録番号を保持する。未登録者は仕入税額控除の扱いが異なるため、明細で区分できるようにする
- **源泉徴収**：リラクゼーションの業務委託は原則として源泉徴収の対象外だが、契約の実態による。フラグで対応できる作りにし、**既定はオフ。判断は税理士に確認すること**

### 11-5. セラピスト向け画面

- **今日の稼ぎ、今月の見込み、確定額。** 施術を完了した瞬間に反映される
- 明細の内訳（コース・指名・オプション・交通費が分かれて見える）
- 過去の支払履歴

**業務委託は自分の報酬が即時に見えることを強く求める。** ここの体験がセラピストの定着に直結するので、管理側の画面より優先度を上げてよい。

### 11-6. 突合

期間 × エリア × セラピストで、**売上 − バック − 経費 = 粗利**を出す。
売上台帳（`revenue_lines`）と報酬台帳（`payout_lines`）は独立して積み、集計時に突き合わせる。片方から他方を導出しない。

## 12. デザイン方針

公開側と管理側で性格が違う。**同じデザインにしない。**

### 12-1. 公開ページ

夜、スマートフォンで、部屋を暗くした状態で見られることが多い。**暗い画面を既定にするのは装飾ではなく機能的な判断。**

| 用途 | 値 |
|---|---|
| 背景 | `#151A20` |
| 面 | `#1E252D` |
| 文字 | `#EDE9E2` |
| 副文字 | `#9BA5AF` |
| 主色（予約ボタン・空き枠） | `#C6A15B`（落ち着いた金） |
| 補助 | `#5E9E86` |
| 罫線 | `#2C343D` |

- 見出し：**Shippori Mincho B1**（明朝）。暗い地に明朝を置くと、清潔さと品を両立できる
- 本文：Noto Sans JP
- 時刻と金額：**IBM Plex Mono**。等幅で縦に揃う

**署名要素**：セラピストカードの「最短 21:30 から案内可能」という表示。ここだけ大きく、金色で、等幅で出す。**このサービスが顧客に約束しているのは結局それ一点**なので、デザインの主役もそこに置く。他は静かに保つ。

**避けること**：クリーム地 × 明朝 × テラコッタの組み合わせ。紫のグラデーション。過度な光沢。煽り文句。効能をうたう表現（第13-2章）。

**必須**
- モバイルファースト。実装も検証もスマホ幅から
- 写真は `next/image`。LCP 2.5秒以内
- セラピストページに構造化データ（`Person`）を入れる
- 予約ボタンは画面下に固定

### 12-2. 管理画面

朝から晩まで見る業務画面。**きれいさより視認性と密度。**

| 用途 | 値 |
|---|---|
| 背景 | `#F6F7F5` |
| 面 | `#FFFFFF` |
| 文字 | `#1C2321` |
| 主色 | `#3F7A6B` |
| 移動時間ブロック | `#B9C2BD`（施術ブロックと明確に区別する） |
| 注意 | `#C98A2B` |
| 警告・遅延 | `#B4453C` |
| 罫線 | `#DFE3DE` |

- 角丸4pxまで。影は使わず罫線で区切る
- アニメーションはドラッグ追従とトーストのみ。画面遷移のフェードは入れない
- `prefers-reduced-motion` を尊重
- 配車ボードは 1280px 以上想定。**ただしセラピスト用の画面は完全にスマホ対応**（移動中に見る）

### 12-3. 文言

- ボタンは動作をそのまま書く。「送信」ではなく「この時間で予約する」
- エラーは何が起きて次に何をすればいいかを書く。謝らない
- 枠が埋まったときは「満席です」で終わらせず、**代替の枠を必ず出す**
- 空の画面には次の一手を置く

## 13. 表記と法令（実装前に決めること）

国家資格を要する施術は扱わず、リラクゼーションとして運営する。これで**あはき法の広告制限は直接の対象外**になるが、代わりに次の3点が設計に効く。**私は弁護士ではないので、最終判断は専門家に確認すること。**

### 13-1. サイト全体の呼称を CMS で一括変更できるようにする ★

リラクゼーション業では、国家資格者の施術と誤認されるのを避けるため「マッサージ」という語を使わず、「ボディケア」「もみほぐし」「リラクゼーション」と表記する事業者が多い。どう名乗るかは事業側の判断だが、**後から全ページの文言を書き換えるのは現実的でない。**

そこで用語辞書を CMS に持ち、公開側のテンプレートは必ずそこを参照する。

```
service_noun    施術の呼称      既定「ボディケア」
staff_noun      担当者の呼称    既定「セラピスト」
session_noun    1回の呼称       既定「コース」
```

**テンプレートにハードコードされた「マッサージ」が1つも無いこと。** レビュー時に grep で確認する。

### 13-2. 公開前の表現チェック

「治る」「治療」「診断」「医療」「効果」「〜が改善します」といった表現は、景品表示法や医薬品医療機器等法の観点で問題になりうる。国家資格と紛らわしい表示も避ける。

CMS の公開ボタンを押したときに、**禁止語リストと照合して警告を出す。** ブロックはせず警告に留め、運営が判断して公開できるようにする。リストは CMS から編集可能にすること。

セラピストのプロフィールは本人や外部ライターが書くことが多く、悪気なく「肩こりが治ります」と書かれる。人力レビューだけに頼らない。

### 13-3. その他

- 特定商取引法に基づく表記、キャンセルポリシーの明示
- **顧客の住所は極めて機微。** 担当セラピストにのみ、予約の3時間前から表示する。閲覧は監査ログに残す。CSV 出力は管理者のみ
- 深夜営業に関する届出

## 15. 必ずテストを書く箇所

- 第5-3章に挙げた空き枠算出の全ケース（最優先）
- 移動時間の時間帯係数、終電跨ぎ
- 仮押さえ：同時2リクエストで片方だけが成功する（実 DB 必須）
- 楽観ロック：古い version での保存が拒否される
- 回数券：発行 → 消化 → 逆仕訳 → 残回数が戻る
- 回数券：端数配分（10,000円3回券が 3,333 / 3,333 / 3,334）
- CMS：項目を追加・非表示にしても既存データが壊れない
- **報酬：レート改定後も、過去に確定した報酬が変わらない**
- **報酬：回数券を消化した施術でもバックが発生する**
- 報酬：個別レート > ランク別 > 既定 の優先順位が正しい
- 報酬：締めたあとの支払がロックされ、修正が逆仕訳になる
- 報酬：`calc_note` に計算根拠が残っている
- オプション：`duration_min` が空き枠計算に反映される
- **オプション：当日の延長で後続予約に間に合わなくなる場合、追加が拒否される**
- 出勤表：出勤していても対応エリア外なら一覧に出ない
- **ポイント：先入先出で古い付与分から消費される**
- ポイント：期限切れが失効し、残高から正しく落ちる
- ポイント：利用分がマイナスの `revenue_line` として立つ
- ポイント：電話注文でも電話番号で識別して貯まる／使える
- ホテル：`extra_minutes` が移動バッファに加算され、空き枠が変わる
- ホテル：`is_blocked` の施設で予約が作れない
- 送信テンプレート：**打診用に住所と電話番号が含まれない**
- 送信テンプレート：差し込み変数が全て埋まる。未定義の変数で落ちない
- 電話受付：既存顧客の自動補完で、住所・好み・NG が正しく引き当たる
- **CMS：トップの見出しと画像を変えると公開ページに反映される**
- CMS：alt 未入力の画像で公開できない
- CMS：掲載同意の無いセラピスト写真が公開されない
- CMS：退職処理でそのセラピストの画像と公開プロフィールが一括で非公開になる
- CMS：お知らせの掲載期間が過ぎると自動で消える
- CMS：ブロックを並べ替えても表示順が保たれる
- CMS：禁止語チェックがサイト文言にもかかる
- **公開側テンプレートに直書きの日本語が存在しない（grep による検査をテスト化する）**
- 不成立ログ：理由なしで保存できない
- 直前割：CMS 設定（時間帯・1日の上限）に従って自動適用され、上限を超えない
- 直前割：割引が `discount` 行として計上され、バック計算の基礎が設定どおりになる
- キャンセル待ち：条件に合う枠が空いたときだけ通知が飛ぶ
- 引き継ぎメモ：次回予約の担当者にだけ表示され、他のセラピストと顧客本人からは見えない
- AI：出力が必ず draft に入り、公開状態を直接変更できない
- AI：構造変更の提案が、承認なしに実行されない
- AI：すべての操作が `ai_actions` に記録される
- locale：既定 `ja` のまま全ページが従来どおり表示される
- 電話確認：未確認の予約では確定用テンプレート（住所入り）が生成できない
- 電話確認：チェックで `phone_confirmed_at` と担当者が記録される
- 電話確認：電話注文は保存時に自動で確認済みになる
- リマインド：前日と2時間前に1回ずつだけ送られる（重複送信しない）
- 経費：入力した経費が突合（売上−バック−経費）に反映される
- 週次レポート：先週分の数字で生成される
- 権限：セラピストが他人の顧客住所と他人の報酬を取得できない

統合テストは**モックではなく実 Postgres** に対して行う。exclusion 制約と RLS はモックでは検証できない。

## 19. CMS 内 AI アシスタント ★

CMS に Anthropic API を組み込み、管理画面の中から AI に作業させる。**できること・できないことを3段階に分けて設計する。分けずに作ると危険なものになる。**

### 19-1. レベル1：コンテンツの生成・編集（実装する）

管理画面の各編集フォームに AI パネルを付ける。

- プロフィール文・キャッチコピー・お知らせ・FAQ・SEO の title / description の下書き生成、リライト、トーン調整
- 画像の alt 文の自動生成
- **禁止語（第13-2章）に触れる表現の検出と、触れない言い換えの提案**
- 用語辞書に従った表記ゆれの統一（「マッサージ」が紛れていたら置換案を出す）

原則：

- **AI の出力は必ず下書き（draft）に入る。AI は公開できない。** 公開ボタンは人間だけが押せる
- AI の出力にも禁止語チェックをかける（AI は制約を破ることがある。二重に守る）
- 生成履歴を `ai_actions` に記録する

### 19-2. レベル2：構造の変更（実装する）

この仕様書は、サイトの多くを**コードではなくデータ**（フィールド定義・ブロック・用語辞書・料金表・テンプレート）で持つよう設計してある。**データであるものは、AI が管理 API 経由で「作り変え」られる。**

できることの例：

- 「セラピストに『対応言語』の項目を足して」 → `field_definitions` に追加
- 「トップのブロックを並べ替えて、キャンペーンのお知らせを一番上に」 → `pages` のブロック更新
- 「12月から全コース500円値上げの改定案を作って」 → 料金改定ドラフト（適用開始日つき）
- 「打診用テンプレートに出発目安を足して」 → `message_templates` の更新

原則：

- 実装は Anthropic Messages API の **tool use** で、**管理画面の Server Action と同じ関数**を叩かせる。AI 専用の抜け道 API を作らない。権限チェック・Zod 検証・監査ログがそのまま効く
- **変更は必ず「差分プレビュー → 人間が承認」を挟む。AI が直接実行しない**
- 破壊的操作（項目の削除、レートの削除、顧客データの変更、一括削除）は AI からは実行不可。提案止まり

### 19-3. レベル3：コード自体の変更（本番システム内ではやらない）

「CMS の機能そのものを作り変える」＝コードの変更は、**稼働中のシステムに自分自身を書き換えさせない。** テストを通らないコードが本番に直行し、セキュリティ検証もマイグレーション管理も飛ぶ。

代わりに、リポジトリ経由の輪を作る：

```
CMS の「改修依頼」ボックスに要望を書く
  → GitHub Issue が自動で立つ
  → Claude Code が Issue を読んで PR を作る
  → CI が通り、人間がレビューしてマージ
  → Vercel が本番へデプロイ
```

「CMS から頼むと機能が増える」という体験はこれで成立し、しかも全変更が履歴・テスト・レビューを通る。

### 19-4. 共通の安全要件

- API キーはサーバー側のみ。クライアントへ一切出さない
- **顧客の個人情報（氏名・電話・住所）を AI へのプロンプトに含めない。** コンテンツ作業に顧客データは不要
- 月間トークン上限を設定し、超過したら停止して管理者に通知する
- 顧客の自由記入など**利用者由来のテキストを AI に読ませる場合はプロンプトインジェクションを想定**する。AI からの操作提案は、内容にかかわらず必ず 19-2 の承認フローを通す
- `ai_actions`：いつ・誰が・何を依頼し・AI が何を返し・何が承認 / 却下されたか

## 付録A. 追加提案（v9 ですべて本文へ採用済み）

以下は本文へ反映済み。**実装は各該当章とフェーズ表に従うこと。** この付録は採用の記録として残す。

1. **不成立ログ（機会損失の記録）** — 電話受付画面に「不成立」ボタンを置き、理由（時間が合わない / エリア外 / 指名不可 / 料金 / その他）をワンタップで記録する。どこで注文を落としているかが数字になり、採用・エリア拡大・料金の判断材料になる。実装コストは最小で効果が大きい
2. **直前割** — 当日埋まらなかった枠に自動で割引を付ける。割引率・対象時間帯・1日の上限枠は CMS で設定。出張型は空き時間がまるごと損失になるため、埋める仕組みの価値が店舗型より大きい
3. **キャンセル待ち（空き通知）** — 満枠時に希望条件（日時・エリア・セラピスト）を登録してもらい、キャンセルで枠が空いたら通知する。キャンセルされた売上を回収する
4. **施術後の引き継ぎメモ** — 完了時にセラピストが一言残す（圧の好み、話題、注意点）。同じ顧客の次回予約時に担当者へ自動表示する。指名以外のリピートの質が上がる
5. **需要ヒートマップと出勤推奨** — 不成立ログ × 曜日 × エリアから「木曜夜の◯◯区は毎週足りない」を検出し、供給ボード（第2-5章）に重ねる。募集とシフト調整が勘でなくなる
6. **CTI（着信ポップ）** — 電話が鳴った瞬間に顧客情報を受付画面に出す。050番号 + API で実現できるが、受付番号の変更を伴うため事業判断。導入すれば電話受付の入力が最速になる
7. **多言語の下準備** — ホテル派遣は訪日客の需要がある。今回は日本語のみでよいが、`pages` と用語辞書に locale カラムだけ先に持たせておく。後から英語版を足すときに作り直しにならない

## 付録B. ロードマップ（承認済み）

1〜4は v1 の本文・フェーズ表へ反映済み。5〜9は **v1 完了後に実装する承認済みロードマップ**（フェーズ24以降）。着手時に本文へ移す。

### v1 に反映済み（1〜4）

1. **予約リマインド通知（前日・2時間前）** — 確定時だけでなく、前日と当日2時間前に自動でメールを送る。無断キャンセルの相当数は「忘れていた」なので、リマインドだけで目に見えて減る。フェーズ20の通知基盤にそのまま載る。**コスト最小・効果大。v1 に入れてよい**
2. **予約ファネル計測** — 公開サイトで「訪問 → セラピスト閲覧 → 枠選択 → 仮押さえ → 確定」の各段階をイベント計測する。どこで離脱しているかが分からないと、サイトの改善が全部勘になる。実装は小さい。**v1 に入れてよい**
3. **週次レポートの自動配信** — 毎週月曜の朝、先週の売上・稼働率・不成立件数・失効間近の回数券/ポイントをオーナーへメールする。集計画面は「見に行く」もので、見に行かなくなる。届くものにする。**v1 に入れてよい**
4. **経費の簡易入力** — オイル・備品・駐車場代・広告費を管理画面から入力できるようにする。突合（売上−バック−経費）の「経費」が現状どこにも入らないため、粗利が実態より良く見える。テーブル1枚と入力画面だけ

### v1 完了後に実装（5〜9）

5. **LINE 公式アカウント連携（打診の自動送信）** — Messaging API で、打診をセラピストの LINE へ自動送信する。**メッセージ本文には顧客の個人情報を一切書かない。**「新しい打診があります」＋期限付き認証リンクだけを送り、詳細の閲覧と受諾はリンク先のセラピスト用マイページ（第7-4章）で行う。LINE は一度送ると消せないため、本文に住所や氏名を書く運用は禁止。これで自動化と個人情報保護が両立し、第8-3章の「LINE に残る」問題も解消する
6. **満足度アンケート（内部向け）** — 施術後に短い星評価+一言をメールで依頼。**公開レビューにはしない**（景品表示法上の論点、やらせ、低評価への報復リスク）。セラピスト品質の内部指標としてランク判定・教育の材料にする
7. **紹介プログラム** — 顧客ごとに紹介コードを発行し、紹介した側・された側の双方にポイント付与。ポイント台帳が既にあるので実装は安い。付与条件（初回施術の完了時）を守ること
8. **採用ページと応募管理** — 求人ページを CMS ブロックで作り、応募フォーム → 管理画面で選考ステータス（応募・面接・研修・稼働）を管理する。需要ヒートマップで「足りないエリア」が見えても、採用の受け皿が無ければ動けない
9. **初回・深夜の事前決済（デポジット）** — 出張型の無断キャンセルは移動時間が丸ごと損失になる。全面オンライン決済はスコープ外のままでよいが、**初回客・深夜帯・高額コースに限って** Stripe の事前決済またはデポジットを検討する。導入判断の基準として、不成立ログと noshow 率を3か月分見てから決めるのがよい
